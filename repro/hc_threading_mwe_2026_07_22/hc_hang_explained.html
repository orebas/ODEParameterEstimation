Incident dossier · scientific‑computing stack

Why the solver freezes when you give it more threads

A single design choice in HomotopyContinuation, run under Julia’s multithreading, ignites a compilation pile‑up that escalates into a genuine runtime‑level hang. Here is the whole chain, from the symptom down to the bytes — and a clear label on every link: which are real bugs, and which only bite when the layers stress each other.

The one‑paragraph version

Every ODEPE solve asks HomotopyContinuation to compile a fresh, one‑off machine‑code routine. Because the fitted coefficients change every time, HC’s cache never recognises the system as “seen before”, so it mints a brand‑new Julia type and recompiles from scratch on every solve. With threading on, the many worker tasks all pile onto Julia’s single global compiler lock — that alone is a multi‑minute freeze. Under enough threads, that same storm of type creation trips a real bug deep in the Julia runtime that corrupts an internal table and turns the temporary freeze into a permanent hang or a segfault. The package everyone blamed for years — MixedSubdivisions, the “Computing mixed cells…” line — is innocent.

§1

What you actually see

A parameter‑estimation run launches a homotopy solve. For roughly a minute it burns all cores at 100%. Then, without an error, every thread goes quiet — CPU drops to nearly zero — and the process sits there for hours. The last line painted on the terminal is almost always:

solve()frozen ≥ 184 s
Tracking 6402 paths...  # progress bar advances, then stops
Computing mixed cells... (no further output — CPU ≈ 0%, held for hours)

Three things make it maddening, and all three are explained by the mechanism in this document:

  • It is nondeterministic. The identical run may finish fine, freeze for minutes, or hang forever. A “heisenbug.”
  • It scales with thread count. Rare or absent at 1–4 threads; common at 8; near‑certain at 14+. This is why the HC maintainer, who runs 2 threads, has never reproduced it.
  • Ctrl‑C is often swallowed. The process still answers OS signals, but won’t interrupt cleanly.
The trap in that last line

“Computing mixed cells…” is not where it hangs. It is a progress meter that HomotopyContinuation leaves switched on for every fresh solve, printing to a side channel. When the process freezes for any reason, that happens to be the last thing painted. Years of debugging aimed at the mixed‑cells code were aiming at the wrong wall. (More in §8.)

§2

What a solve really does — from the machine’s side

You already know the math side: differentiate‑then‑solve turns a model into a polynomial system, and HomotopyContinuation tracks paths to its roots. This document is about what happens underneath that call, in the compiler and the thread scheduler — the layer that’s biting us. Here is the path of one solve:

Polynomial systemfrom ODEPE, distinct numeric coefficients each solve
→
CompiledSystemHC generates + compiles a machine‑code evaluator
→
N tracker tasksthreading=true spawns one per core
→
Follow pathseach task runs the compiled evaluator millions of times

The second box is the whole story. To evaluate a polynomial system as fast as possible, HC doesn’t interpret it — it writes out a straight‑line program (a flat list of arithmetic ops) and hands it to Julia’s compiler, which runs it through LLVM to native code. ODEPE explicitly asks for this on every system, in src/core/homotopy_continuation.jl:

homotopy_continuation.jl:415, :651
HomotopyContinuation.set_default_compile(:all)   # compile every system to native code
_hc_solve(args...; kwargs...) = HomotopyContinuation.solve(args...;
    threading = HC_SOLVE_THREADING[], kwargs...)      # and spawn N worker tasks
Primer · task vs. thread, and what threading=true buys

A Task is a unit of work Julia can run concurrently; the runtime’s scheduler parks tasks onto OS threads (you pick how many with julia -t N). threading=true tells HC to split its thousands of homotopy paths across N worker tasks so they track in parallel. On this workload that’s a real, measured 2.63× speedup with bit‑identical results — which is exactly why “just turn threading off” is the wrong answer. We want the threads. We want the bug fixed.

§3

The ignition — a brand‑new type on every single solve

Here is HC’s constructor for a compiled system (trimmed to the essential lines, from the active HomotopyContinuation 2.20.0 source, model_kit/compiled_system_homotopy.jl):

compiled_system_homotopy.jl:1, 39–57
const TSYSTEM_TABLE = Dict{UInt,Vector{System}}()   # a global cache, keyed by a hash

function CompiledSystem(F::System)
    # names are cleared so identical structure -> identical code...
    cleard_exprs = subs(expressions(F), D)
    h = hash(cleard_exprs)          # <-- coefficients are STILL in here
    if haskey(TSYSTEM_TABLE, h)         # seen this exact system before?
        # ... find index k ...
    else
        k = 1
        TSYSTEM_TABLE[h] = [sys]         # otherwise store it
    end
    return CompiledSystem{(h, k)}(n, nvars, nparams, F)  # type carries (hash, index)
end

Look at the return line. The identity of the system — the pair (h, k) — is baked into the type parameter, not stored as ordinary data. That is a deliberate and clever trick: it lets HC’s generated evaluator recover the exact system at compile time straight from the type, which is how the straight‑line program gets specialised per system. The TSYSTEM_TABLE cache exists to make it cheap: solve the same system twice and you reuse the same (h, k), the same type, the same already‑compiled code.

Why the cache never helps ODEPE

The hash h is taken over expressions that still contain the fitted numeric coefficients. Every ODEPE solve has different coefficients, so every solve produces a different h, a different (h, k), and therefore a type Julia has never seen. A cache that only hits on exact repeats can’t hit a workload that never repeats. Result: every solve triggers a full, from‑scratch compile of all the tracker methods, specialised on a fresh type.

This is the ignition source for everything that follows. Note carefully: on its own it is not a bug. It’s a reasonable design — per‑system compiled code is genuinely fast — whose cache assumption happens to be wrong for our workload. What makes it dangerous is that it hands two lower layers a stimulus they don’t handle well under concurrency. That’s the next three sections.

Stress source · not itself a defect

§4

Failure mode 1 — the compilation convoy

Every solve recompiles; the workers queue behind one lock Emergent pathology

When solve spawns its N tracker tasks, each one calls methods specialised on the fresh CompiledSystem{(h,k)} type. Since that type is new, none of those methods are compiled yet — so all N tasks demand compilation of the same code at the same moment.

Primer · why compiling is a single‑lane road

Julia compiles lazily: the first call to a method on a given set of types triggers type inference and LLVM code generation. To keep that process consistent, the runtime guards it with one global lock, jl_typeinf_lock. Two threads cannot infer at the same time — one holds the lock and works, the rest wait. Normally that’s invisible, because compilation happens once and is then cached. Here it happens on every solve, for a big freshly‑typed method, across all cores at once.

So the N tasks form a convoy: one thread grabs jl_typeinf_lock and starts compiling; the other 13 park behind it. And the one doing the work can take a very long time, because the generated evaluator for a large system (think a 32×32 jet system) is an enormous straight‑line function, and LLVM’s vectorizer is super‑linear on such code. Here is the actual state of a frozen process, captured with gdb — a sequential, production‑shaped solve (one solve at a time, exactly how ODEPE issues them), stuck for over three minutes:

This is the picture the whole investigation was missing. It is not a deadlock in the textbook sense — there’s no cycle of locks waiting on each other. It is a convoy: 13 cores idling while 1 core grinds through a pathological compile, for minutes, with the “Computing mixed cells” meter frozen mid‑paint. To an operator (or a watchdog) that is indistinguishable from a hang.

Layer: Julia compiler behaviour, provoked by HC Trigger: fresh type every solve × threading × large system Bites ODEPE’s real (sequential) path: yes

On its own the convoy is “only” slow — given enough patience the compile finishes. The reason it so often becomes permanent is the next layer down.

§5

Failure mode 2 — the runtime corruption (the real bug)

Concurrent type creation corrupts a shared runtime table Clear bug · Julia runtime

Minting CompiledSystem{(h,k)} forces Julia to instantiate a parametric type whose parameter is a fresh (UInt, Int) tuple. When many tasks do that at once — which is exactly what the convoy above causes — they collide inside a global runtime table and corrupt it.

Primer · apply_type and the “global roots” table

When Julia builds a type like Foo{(123, 4)}, the runtime function apply_type runs. To avoid keeping millions of duplicate type‑parameter objects alive, it interns each new one into a shared hash set — the global roots idset. That set is grown by re‑hashing. If two threads re‑hash it at the same moment without proper synchronisation, its internal probe sequence is left inconsistent: a lookup then either loops forever over a broken chain (a hang) or dereferences a bad slot (a segfault).

We isolated this to 30 lines of pure Julia with no HomotopyContinuation at all — the essence of what CompiledSystem{(h,k)} does to the runtime, and nothing else:

typeinst_control.jl — stdlib onlythe JuliaLang MWE
struct Foo{T} end

function worker(w)
    for i in 1:N
        h = rand(rng, UInt)      # fresh random bits, like hash(exprs)
        T = Foo{(h, i % 8 + 1)}    # instantiate a fresh (UInt,Int)-param type
    end
end
@sync for w in 1:NW           # run that on every worker task at once
    Threads.@spawn worker(w)
end

Run at high thread counts, it hangs or crashes on this machine, reliably, with a monotone thread‑count gradient. These are the outcomes across both the sub‑agent’s campaign and an independent re‑run:

Why this is labelled a clear Julia bug

No user code did anything illegal. Instantiating types concurrently is supposed to be safe, and here it demonstrably is not — with zero HomotopyContinuation involved. It reproduces on both Julia 1.11.5 and 1.12.6, so it is long‑standing, not a 1.12 regression. The backtrace matches the closed issue JuliaLang/julia#58171 (filed for 1.11 / PythonCall), whose supposed fix (PR #57392) evidently did not fully close the concurrent path — our stdlib‑only reproducer on 1.12.6 proves it’s still live.

§6

Failure mode 3 — HC’s unlocked caches

Two global Dicts are mutated from threads with no lock Clear bug · HomotopyContinuation

Look again at that cache from §3. TSYSTEM_TABLE (and its twin THOMOTOPY_TABLE) is a plain Base.Dict, and the constructor reads and writes it — haskey, push!, setindex! — with no synchronisation whatsoever.

Primer · why a shared Dict is a landmine

Julia’s Base.Dict is explicitly not thread‑safe. When it fills up it rehashes into a bigger array; if a second thread reads or writes during that rehash, entries land in the wrong buckets or vanish. This is a classic data race: no error, just silently wrong data — a CompiledSystem whose cache entry later resolves to the wrong system, or a KeyError, or a crash.

Measured directly, by constructing distinct systems concurrently and counting how many cache entries survive (they should all survive — construction count equals entry count with no races):

12 workers × 60,000 constructions = 720,000 expected entries, -t 14. Lost entries are silent time‑bombs; each one is a future wrong‑system or crash.

Clear bug — but read the fine print for ODEPE

Mutating a shared Base.Dict without a lock is unambiguously a bug, and the fix is trivial (a ReentrantLock around the table — five lines). But it only bites when construction happens concurrently. ODEPE issues its solves one at a time, on a single task, so the writes are effectively serialised — this race is a real fleet‑scale hazard (many solves in one process, or any future concurrent use), not the thing freezing your sequential runs today. That distinction is the point of this whole document: same code, different blast radius depending on how the layer above stresses it.

§7

How the three stack up

None of these fires in isolation on a normal machine. The observed hang is a chain: a non‑bug design choice at the top drives an emergent pathology in the middle, which under load detonates a real bug at the bottom.

1Fresh CompiledSystem{(h,k)} per solvestress source

Coefficients in the hash ⇒ the cache never hits ⇒ a type Julia has never seen, on every solve.

2Compilation convoyemergent

All N tracker tasks demand the fresh method’s compilation at once → they queue on jl_typeinf_lock while one core grinds LLVM. Minutes of frozen, near‑zero‑CPU wall time. This alone is what ODEPE’s sequential runs hit.

3Runtime corruption tripsclear bug

That same storm of fresh‑type creation races the global‑roots idset (§5). With ≥8 threads the odds cross over: the temporary convoy becomes a permanent spin — and a spinning thread never reaches a GC safepoint, so it freezes every other thread too.

4Permanent hang, or segfaultwhat you see

Zero CPU, held for hours, “Computing mixed cells…” frozen on screen. Or, if the corrupted probe hits a bad slot instead of looping, an outright crash.

Primer · why a spinning thread freezes the whole process

Julia’s garbage collector is “stop‑the‑world”: to run, it must pause every thread at a safepoint. Threads reach safepoints at allocations and back‑edges. A thread stuck spinning inside a corrupted idset probe loop allocates nothing, so it never reaches a safepoint — and the next time any thread needs a GC, it waits forever for the spinner. One corrupted probe loop → the entire process wedged. That is the bridge from “failure mode 2” to “the whole thing is frozen.”

This chain explains all three mysteries from §1 at once. Nondeterministic: whether the idset race corrupts anything is a timing coin‑flip. Thread‑count gradient: more threads = more simultaneous type creation = higher odds the coin comes up bad — clean at 2–4, near‑certain at 14. Maintainer can’t reproduce: two threads sits below the threshold where the odds bite.

§8

What it is not — exonerations

A lot of prior effort (mine included) chased suspects that turn out to be innocent. Ruling them out is part of the result, and it matters for anything we post upstream.

MixedSubdivisions — the “Computing mixed cells” packageExonerated

A full grep of MixedSubdivisions 1.1.5 and 1.2.0 finds zero threading primitives — no @spawn, no threadid, no locks. It is entirely serial and cannot host a threading bug. Its progress meter defaults to on and HC never turns it off, so it merely happens to be the last line painted when the process freezes elsewhere. Years of suspicion, misdirected by a status line.

The Julia scheduler / “partr notify‑race” (issue #59538)Ruled out

There is a real 1.12 scheduler deadlock of that family (#59538), which briefly looked like the culprit — but it was a startup deadlock, fixed by PR #59583 and shipped in 1.12.1 and every release since. We’re on 1.12.6, which contains the fix. Our freeze is not a scheduler notify‑race; it’s the type‑instantiation path in §5. (This was my own leading theory for a while. It was wrong.)

HC’s old threadid() indexing bug (issue #668)Ruled out

Fixed by HC’s PR #669 threading rework; the current 2.20 solve path has no threadid indexing at all.

Two harmless‑but‑real oddities were also noted in passing: ProgressMeter 1.11’s threadid()‑based locking heuristic can garble output under task migration (corruption, not a hang), and HC’s started counter at solve.jl:639 is never incremented, so an interrupted solve collects zero results (cosmetic).

The taxonomy, and where each fix lives

Pulling every finding into one table, with the label you asked for — a plain defect, versus something that only surfaces when another layer leans on it:

Fixes, from deepest to most immediate

JuliaLang (the deepest bug). Report the concurrent‑apply_type / global‑roots race with typeinst_control.jl — a 30‑line, dependency‑free reproducer with a clean thread‑count gradient on 1.11.5 and 1.12.6. This is the fix that would help every package, not just HC. Attach to / reopen the #58171 thread.

HomotopyContinuation. Two things: (a) put a lock around the two cache Dicts — a clean five‑line PR that closes the §6 corruption; (b) more importantly for the convoy, compile the CompiledSystem evaluator once on the setup task, before the tracker tasks are spawned — that serialises the unavoidable compile onto one thread instead of an N‑way pile‑up on jl_typeinf_lock, keeping the fast‑evaluation design intact. Note honestly: the (h,k)‑in‑the‑type trick can’t simply become a field, because it’s what drives per‑system codegen — so the per‑distinct‑system compile cost is somewhat inherent; the real lever is not paying it N times concurrently per solve.

ODEPE, to unblock today (without giving up threads):

  • Switch to interpreted systems (compile=:none). No per‑system codegen means no convoy and no fresh‑type storm at all. For one‑shot, coefficient‑varying solves this is often faster overall, because it skips the compile you were never able to amortise — worth a direct benchmark.
  • Re‑cast as a parameter homotopy — put the varying coefficients in as HC parameters rather than baked constants, so the structure is fixed, the hash is stable, and exactly one compiled type is reused across all solves. The γ‑straight / generic‑start work already leans this way.
  • Last resort only: one thread per solver process. It dodges the bug but throws away the measured 2.63× — which is precisely the trade we’re trying not to make.
